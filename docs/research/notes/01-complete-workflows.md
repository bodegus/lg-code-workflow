## 1. LangChain Open SWE (`langchain-ai/open-swe`)

Borrowable details from v1 (**verified**):
- **Structured reviewer verdict via forced tool choice** — [`reviewer/nodes/final-review.ts` L119-L223](https://github.com/langchain-ai/open-swe/blob/f1546093513aa49a5d88c8322a84a32452e537d3/apps/open-swe/src/graphs/reviewer/nodes/final-review.ts#L119-L223): the model is bound to exactly two tools (`code_review_mark_task_completed` / `code_review_mark_task_not_complete{additional_actions[]}`) with `tool_choice: "any"`; "not complete" appends new plan items and increments `reviewsCount`. The routing after the reviewer is pure code (`routeGenerateActionsOrEnd`: all plan items complete → conclusion, else back to the builder).
- **Bounded review loop in code**, not prose: `maxReviewCount ?? 3` in `routeToReviewOrConclusion` ([programmer/index.ts L114-L128](https://github.com/langchain-ai/open-swe/blob/f1546093513aa49a5d88c8322a84a32452e537d3/apps/open-swe/src/graphs/programmer/index.ts#L114-L128)).
- **Stuck detection**: `lastMessagesMissingToolCalls(messages, 2)` — two consecutive AI turns without tool calls ends the action loop even if plan items remain (L26-L36, L90).
- **PR opening is a node, but not LLM-free**: [`programmer/nodes/open-pr.ts`](https://github.com/langchain-ai/open-swe/blob/f1546093513aa49a5d88c8322a84a32452e537d3/apps/open-swe/src/graphs/programmer/nodes/open-pr.ts) checks `git diff --name-only` deterministically, commits/pushes with the **GitHub App installation token from config** (L97, L143-L153), then calls a small "router" model with a forced `open_pr` tool only to write title/body (L158-L200), then `createPullRequest`/`updatePullRequest` (L216-L237) and deletes the sandbox. Body gets `Fixes #<issue>` prepended in code (L214).
- **No CI loop in v1.** v1 never polled checks; `SKIP_CI_UNTIL_LAST_COMMIT` only pushes an empty commit (L194-L198). The PR was the end state.
- Sandbox: Daytona (cloud); auth: GitHub App (installation token + user OAuth), LLM API keys per user (Anthropic/OpenAI/Google). No ChatGPT-OAuth path (**verified** README "you're required to set your own LLM API keys").

### 1b. Open SWE v2 (Python, Feb 2026 – now) — one Deep Agent + middleware, not a pipeline graph

Timeline (**verified** via `gh api search/commits`): v1 deprecated 2026-01-26; "Add Python agent with LangSmith sandbox support" `b2c466df` 2026-02-04; "switch from deepagents-cli to deepagents library" 2026-02-09 (#924); "authenticate git operations via sandbox proxy instead of credential files" 2026-04-07 (#1070); "stop auto-cloning and let agent manage repo setup" 2026-04-10 (#1159). Main at research time: `0942b415` (2026-10-13). Pinned deps (**verified**, [`pyproject.toml`](https://github.com/langchain-ai/open-swe/blob/0942b41561df7db968f3be7f1c5150819bdec6b8/pyproject.toml)): `deepagents==0.7.21`, `langgraph>=1.2.12`, `langchain[mcp]>=1.4.4`, `langchain-openai>=1.6.5`, Python ≥3.14, `githubkit[auth-app]==0.16.1`, `langgraph-checkpoint-sqlite`.

README now calls it "an open-source software factory built on Deep Agents" and (**verified**) says: "Deep Agents supplies planning, filesystem, shell, skills, and subagent primitives. LangGraph provides durable execution and thread state."

**Graph entry points** ([`langgraph.json`](https://github.com/langchain-ai/open-swe/blob/0942b41561df7db968f3be7f1c5150819bdec6b8/langgraph.json)): `agent`, `reviewer`, `review-scout`, `chat`, `scheduler` — each a *factory* returning a `create_deep_agent(...)` graph (e.g. [`openswe/server.py` L2097-L2244](https://github.com/langchain-ai/open-swe/blob/0942b41561df7db968f3be7f1c5150819bdec6b8/openswe/server.py#L2097-L2244)). There is **no** explicit issue→build→review→CI StateGraph any more. The process lives in prompts, skills and ~35 middleware classes (prepare-run, model fallback, `ModelCallLimitMiddleware(exit_behavior="end")`, `PullRequestCreationGuardMiddleware`, `WorkflowPushGuardMiddleware`, `RequireUserReplyMiddleware`, message-queue injection, …).

The customization guide states the philosophy explicitly (**verified**, [`docs/CUSTOMIZATION.md` §6](https://github.com/langchain-ai/open-swe/blob/0942b41561df7db968f3be7f1c5150819bdec6b8/docs/CUSTOMIZATION.md)): "There is intentionally no after-agent middleware that opens a PR for the agent. The agent is responsible for committing, pushing, opening/updating the draft PR, and replying in the source channel. If you want a deterministic backstop for your fork, add an `@after_agent` hook here." → **This is the opposite of what we want** (it is essentially our current "LLM conductor follows prose" model, but with a much richer middleware safety net).

- **S7** — separate `reviewer` deep agent ([`openswe/reviewer.py`](https://github.com/langchain-ai/open-swe/blob/0942b41561df7db968f3be7f1c5150819bdec6b8/openswe/reviewer.py)): deterministic repo prep + diff computation *before* the first model call (`prepare_reviewer_run`), reviewer-only tools `add_finding/update_finding/list_findings/publish_review`, "No commit/push/PR-opening tools". `add_finding` ([`openswe/tools/add_finding.py`](https://github.com/langchain-ai/open-swe/blob/0942b41561df7db968f3be7f1c5150819bdec6b8/openswe/tools/add_finding.py)) validates severity ∈ {low,medium,high,critical}, confidence ∈ {low,medium,high}, and rejects findings whose lines are not in the PR diff — structured output enforced by a tool, not by parsing prose.

#### The `/baby-sit` CI watch (S6) — deterministic, copyable (MIT)
All **verified** in [`openswe/baby_sit.py`](https://github.com/langchain-ai/open-swe/blob/0942b41561df7db968f3be7f1c5150819bdec6b8/openswe/baby_sit.py) and [`openswe/github/ci.py`](https://github.com/langchain-ai/open-swe/blob/0942b41561df7db968f3be7f1c5150819bdec6b8/openswe/github/ci.py):
- `aggregate_check_state(check_runs, statuses) -> pending | success | blocked | failure` — a pure function over the check-runs API **and** the legacy commit-status API (`baby_sit.py` L390-L410). "No checks yet" is `pending`, not success. Non-success, non-failing terminal conclusions (e.g. `cancelled`, `stale`) are `blocked` → human triage.
- `FAILING_CONCLUSIONS = {"failure","timed_out","action_required"}`; Open SWE's own check runs are excluded (`ci.py` L28-L31).
- `RequiredCheck.for_branch()` reads **both** classic branch protection and **rulesets** (`ci.py` L61-L103); `unreported_required_checks()` keeps the state `pending` until every required check has reported on the head SHA (`baby_sit.py` L490-L495). This avoids the classic "green because the required job hasn't started yet" bug.
- Triggered by CI webhooks (`check_run`, `check_suite`, `workflow_run`, `status` completed) **plus** a `*/10 * * * *` cron fallback that "consumes no model tokens while state is unchanged" (`bundled_skills/baby-sit/SKILL.md`).
- Idempotency/bounds: per-head-SHA retry counter reset when the head changes; `MAX_RETRIES_PER_HEAD = 3`; failure fingerprint `sha256(head_sha|retry:N)` stored as `dispatch_keys`; webhook `delivery_id` dedupe; `MAX_EVALUATION_ERRORS = 3` then stop; a lock implemented by creating a LangGraph thread with a fixed ID (conflict ⇒ busy) (`baby_sit.py` L41-L68, L454-L535).
- On failure it dispatches an LLM run with a prompt that wraps check names/URLs in `<untrusted-ci-data>` and tells the agent to read only failed-job logs with `gh run view <id> --log-failed` ([`resources/prompts/runs/baby-sit-failure.md.jinja`](https://github.com/langchain-ai/open-swe/blob/0942b41561df7db968f3be7f1c5150819bdec6b8/openswe/resources/prompts/runs/baby-sit-failure.md.jinja)). Note: in Open SWE the *LLM* fetches the log; in our design a deterministic node should fetch it and pass it in.

#### Credential-isolation pattern worth copying: reviewer on "Managed Deep Agents"
[`mda/reviewer/README.md`](https://github.com/langchain-ai/open-swe/blob/0942b41561df7db968f3be7f1c5150819bdec6b8/mda/reviewer/README.md) (**verified**): the reviewer's model loop and sandbox run in a deployment that "holds no GitHub, Slack or database credentials"; its tools are served back over MCP by the trusted backend; "Dispatch signs a run token into the context of each reviewer run… The backend reads the thread, repository and pull request from the token, never from tool arguments." That is exactly our "agent loops don't hold GitHub write credentials" rule, implemented as: untrusted loop → MCP tool server → scope taken from a signed token, not from model-chosen arguments.

### 1c. Verdict on Open SWE for our prototype
- **Do not adopt Open SWE wholesale.** v2 is a ~900-file multi-tenant product (Postgres, Slack, dashboard, LangSmith sandboxes/tracing, Agent Server licence for production standalone) whose *process* is LLM-driven — the same failure mode we are trying to leave. v1 had the explicit graph shape we want but is TypeScript, deprecated, has no CI loop, and its planner/programmer split is heavier than we need.
- **Do copy (MIT, attribute):** `openswe/github/ci.py` (check aggregation, required checks incl. rulesets, webhook payload parsing) and the `aggregate_check_state` + per-head retry/fingerprint logic of `openswe/baby_sit.py`; the reviewer's *deterministic prep → bounded LLM loop → tool-enforced structured findings* shape (`openswe/reviewer.py`, `openswe/tools/add_finding.py`, `openswe/review/diff.py`); v1's forced-tool-choice verdict (`final-review.ts`) and `maxReviewCount` routing; `local_checkpointer.py` as a reminder that `langgraph dev` is not durable.
- **Do copy the security idea, not the code:** sandbox never sees tokens (proxy-injected auth) and the MDA reviewer's "scope from signed run token, never from tool arguments".

## 2. LangChain Deep Agents (`langchain-ai/deepagents`) and its coding-agent pieces

**Repo facts (verified 2026-10-13):** 30,201 stars, 4,235 forks, MIT, last push 2026-10-13; releases `deepagents==0.7.24` (2026-10-12), `deepagents-code==0.1.84` (2026-10-12), `deepagents-acp==0.0.13`. Description: "The batteries-included agent harness." Monorepo `libs/`: `deepagents` (core), `code` (the CLI **`deepagents-code` / `dcode`**; its CHANGELOG says it "was forked from `deepagents-cli` at v0.1.0 (2026-05-12)" and `libs/cli` is no longer in the tree), `acp` (Agent Client Protocol server), `talon`, `evals`, `partners` (sandbox integrations).

What it gives a builder/reviewer *loop* (all **verified** in `libs/deepagents/deepagents/`):
- `create_deep_agent(model, tools, system_prompt, subagents, middleware, backend, interrupt_on, permissions, skills, memory, …)` returns a compiled LangGraph graph — usable as a **node or subgraph** inside our deterministic StateGraph.
- Backends: `LocalShellBackend` (host shell, no isolation), `FilesystemBackend`, `StateBackend`, `StoreBackend`, `CompositeBackend`, `sandbox.py` protocol (+ partner packages `langchain-daytona`, `langchain-modal`, `langchain-runloop`, `langchain-e2b`) and `langsmith.py` (LangSmith sandboxes).
- Middleware: `subagents`, `async_subagents`, `filesystem`, `summarization`, `skills`, `memory`, `permissions`, `patch_tool_calls`, and **`rubric.py`** — `RubricMiddleware`: when the agent would finish, a separate grader sub-agent scores the transcript against a rubric; `needs_revision` injects feedback and resumes; terminal statuses `satisfied | failed | max_iterations_reached | grader_error`; criteria frozen after the first pass; an incomplete "satisfied" is downgraded ([`middleware/rubric.py`](https://github.com/langchain-ai/deepagents/blob/main/libs/deepagents/deepagents/middleware/rubric.py), `@beta`). Good model for a *self-check inside S3*, not a replacement for our S7 reviewer.
- Harness profile for OpenAI Codex models (`profiles/harness/_openai_codex.py`: gpt-5.1/5.2/5.3-codex prompt suffix).

Coding-agent artefacts:
- **`dcode` GitHub Action** ([`ACTION.md`](https://github.com/langchain-ai/deepagents/blob/main/ACTION.md), `action.yml`): runs `dcode` headless in Actions with `prompt`, `model`, `*_api_key`, `shell_allow_list` (e.g. `recommended,git,gh`), `max_turns`, `task_timeout`, `json` output, memory persisted via `actions/cache`. Comparable to `codex exec`/claude-code-action as a one-shot builder step. API keys only in the Action (no OAuth input listed).
- `dcode` CLI supports **ChatGPT OAuth sign-in for Codex models** (see §1d) and remote sandboxes; useful as a *local builder runner* for S3 if we would rather shell out than embed.
- [`examples/deploy-coding-agent`](https://github.com/langchain-ai/deepagents/tree/main/examples/deploy-coding-agent): "Plan → Implement → Review → Deliver" — but the workflow is **prose in `AGENTS.md` + skills**, deployed with `deepagents deploy` on LangSmith. Demo, not a pipeline.
- [`examples/ralph_mode`](https://github.com/langchain-ai/deepagents/tree/main/examples/ralph_mode): fresh-context loop (`while :; do cat PROMPT.md | agent; done`) with `--iterations`, `--sandbox modal|daytona|runloop|agentcore`, `--shell-allow-list`. Demo; relevant only as the "restart with fresh context each iteration, state in git" idea for S3 retries.
- `examples/rubric_middleware`, `examples/better-harness` (harness optimisation), `examples/async-subagent-server`.

**Assessment:** Deep Agents is the right *library for the S3/S7 agent loops* (it is what Open SWE uses), but LangChain ships **no deterministic issue→PR pipeline template** on top of it; every LangChain coding example puts the process in prompts. The deterministic outer graph is ours to write.

## 3. Other LangGraph-based issue-to-PR / CI-fix / review systems

### 3a. GitLab Duo Agent Platform / Duo Workflow Service — **serious, production, LangGraph, but source-available (not open source)**

**Facts (verified via GitLab API, 2026-10-13):** project `gitlab-org/modelops/applied-ml/code-suggestions/ai-assist` ("AI Gateway"), public, 61 stars / 118 forks (GitLab counts), last activity 2026-10-13, very active. **Licence: "GitLab Enterprise Edition (EE) license"** — "you may copy and modify the Software for development and testing purposes", production use needs an EE subscription, and "it is forbidden to copy, merge, publish, distribute, sublicense, and/or sell the Software" ([LICENSE](https://gitlab.com/gitlab-org/modelops/applied-ml/code-suggestions/ai-assist/-/blob/main/LICENSE)). ⇒ **Read for design; do not copy code.** The old standalone repo `gitlab-org/duo-workflow/duo-workflow-service` is archived and was merged here.

Architecture (**verified**, [`duo_workflow_service/README.md`](https://gitlab.com/gitlab-org/modelops/applied-ml/code-suggestions/ai-assist/-/blob/main/duo_workflow_service/README.md)): a Python gRPC service that "manages and executes AI-powered workflows using LangGraph… maintaining workflow state through periodic checkpoints saved to GitLab… maintaining a secure boundary between untrusted code execution and the core GitLab infrastructure". Commands run in a separate **Duo Workflow Executor** that the service drives (in the IDE or a CI runner — *inferred*, not stated in that README); checkpoints go to GitLab through a custom `BaseCheckpointSaver` (`duo_workflow_service/checkpointer/gitlab_workflow.py`).

Two generations, both instructive:

1. **Hand-written StateGraphs** (`duo_workflow_service/workflows/`): `issue_to_merge_request`, `software_development`, `convert_to_gitlab_ci`, `chat`. [`issue_to_merge_request/workflow.py`](https://gitlab.com/gitlab-org/modelops/applied-ml/code-suggestions/ai-assist/-/blob/main/duo_workflow_service/workflows/issue_to_merge_request/workflow.py) (**verified**): `build_context` (LLM + read-only tools ⇄ `build_context_tools`, router on tool name, `handover_tool` to exit) → `PlannerComponent` → `set_status_to_execution` → `ExecutorComponent` with a `ToolsApprovalComponent` (human approval of tool calls) → **`git_actions` = a deterministic `RunToolNode`** running `git add -A`, `git commit -m 'Duo Workflow: Resolve issue #<iid>'`, `git fetch --unshallow`, `git push` → END. Status checks (`CANCELLED`/`ERROR` → `plan_terminator`) are in plain routers. Tool lists are per role (context builder / planner / executor) — least privilege per node. Compiled with `graph.compile(checkpointer=checkpointer)`.

2. **Declarative YAML "Flow Registry"** compiled to LangGraph (`duo_workflow_service/agent_platform/v1/`): component types `AgentComponent` (LLM loop, optional `response_schema_id` for a structured `final_answer`, `max_cycles`, `identical_tool_call_limit`), **`DeterministicStepComponent`** (one tool call, literal inputs, no LLM), `OneOffComponent` (single LLM tool call with `max_correction_attempts`), `HumanInputComponent`, `SupervisorComponent`, `ForEach`; plus `routers` with `condition: {input: "context:<component>.final_answer.decision", routes: {...}, default_route}`. The [`fix_pipeline/1.0.4.yml`](https://gitlab.com/gitlab-org/modelops/applied-ml/code-suggestions/ai-assist/-/blob/main/duo_workflow_service/agent_platform/v1/flows/configs/fix_pipeline/1.0.4.yml) flow (**verified**) is the closest public analogue to our S6→S3 loop:
   `fetch_failing_jobs` (deterministic `get_pipeline_failing_jobs`) → `fetch_failing_bridge_jobs` (deterministic) → [`fetch_mr_diffs` if an MR URL exists] → `fix_pipeline_context` (agent, structured `decision ∈ {add_comment, create_plan, direct_code_suggestions, no_action}`) → … → `fix_pipeline_execution` (agent with edit/run tools) → `fix_pipeline_check_diff` (deterministic `git diff`) → `fix_pipeline_decide_fix` (agent with **empty toolset**, structured decision) → `git_fetch_for_branch`/`git_fetch_unshallow` (deterministic) → `fix_pipeline_create_branch` → `fix_pipeline_create_new_mr` (`OneOffComponent`, `max_correction_attempts: 3`) → comment → end. **Every branch decision is a router over a schema-validated field, never free text.**

Lessons recorded by the GitLab team (**verified**, [`developer/PRINCIPLES.md`](https://gitlab.com/gitlab-org/modelops/applied-ml/code-suggestions/ai-assist/-/blob/main/duo_workflow_service/agent_platform/v1/flows/configs/developer/PRINCIPLES.md)): "The system prompt states principles, not procedures"; "When the agent misbehaves, first find the layer that owns the failure — the goal, the tool contract, the toolset, the environment setup… Add a prompt instruction only when the failure is universal"; "Match the environment to the distribution first" (full checkouts, familiar shell tools). Their general `developer` flow v2/v3 collapsed to **one `AgentComponent`** (v2: deterministic `git_unshallow` → `developer_agent` → end; v3: just the agent, with an authenticated `glab`). I.e. GitLab keeps *task-specific* flows as explicit graphs with deterministic steps, while the generic coding step is one agent — the same split we are proposing (deterministic outer graph, one builder agent inside). Two more task flows I checked (**verified** component lists): `code_review/3.0.0.yml` = deterministic `build_review_context`, `fetch_mr_diffs`, `fetch_mr_metadata`, `fetch_existing_discussions` + `OneOffComponent` prescan + `AgentComponent` `analyze_prescan_results` + `OneOffComponent` `perform_code_review_and_publish` (a good S7 template: fetch everything deterministically, let the LLM only judge and emit one structured publish call); `resolve_sast_vulnerability/1.0.3.yml` = deterministic `gather_context`, `resolve_target_branch`, `exclude_pre_existing_files`, **`validate_fix_has_changes`** (after the `execute_fix` agent — a cheap "did the builder change anything?" gate), `link_vulnerability`, with agent/one-off components for branch, commit, push and MR.

Mapping: S1 (issue fetch in context builder), S2 (executor workspace / CI runner), S3 (executor agent), S4 (none built in), S5 (deterministic `git_actions`, MR creation via `create_merge_request` tool / `OneOffComponent`), S6 (`fix_pipeline` flow, triggered by a failed pipeline), S7 (`code_review`, `deep_code_review` flows), S8 (not chained automatically), S9 (MR creation; no auto-merge seen), S10 (`ToolsApprovalComponent`, `HumanInputComponent`), X (GitLab-hosted checkpoints, service/executor split). Auth: GitLab tokens + Anthropic/Vertex via the AI Gateway; no ChatGPT OAuth.

### 4f. GitHub Copilot cloud agent (formerly "coding agent") — public safety design
**Verified** in [Risks and mitigations](https://docs.github.com/en/copilot/concepts/security-governance-and-network-settings/risks-and-mitigations) and [About the agent](https://docs.github.com/en/copilot/concepts/agents/coding-agent/about-coding-agent) (fetched 2026-10-13):
- Starts from an issue/PR/agents panel; runs in "an ephemeral cloud development environment" with tests and linters (Actions-based — *inferred* from the page's reference to a `copilot-setup-steps` file with `timeout-minutes`); one repository per task; **59-minute session cap**.
- "Copilot cloud agent only has the ability to push to a single branch" (usually a new `copilot/…` branch); "**can only perform simple push operations. It cannot directly run `git push` or other Git commands.**" (push is mediated by the platform, not a credential in the sandbox).
- "Draft pull requests… must be reviewed and merged by a human. Copilot cloud agent **cannot mark its pull requests as 'Ready for review'** and cannot approve or merge a pull request."
- "By default, **workflows are not triggered** until Copilot cloud agent's code is reviewed and a user with write access… clicks **Approve and run workflows**."
- Internet firewall; hidden characters (e.g. HTML comments) filtered from input; only users with write access can trigger; commits co-authored by the requester; self-checks with CodeQL, advisory DB, secret scanning and a Copilot code-review "second opinion" before finishing.
- **Note for S5/S6:** the "Approve and run workflows" gate above is Copilot-specific. For our own publisher the documented pitfall is the token type: "events triggered by the `GITHUB_TOKEN` will not create a new workflow run" (except `workflow_dispatch`/`repository_dispatch`; PR `opened/synchronize/reopened` runs are created in an approval-required state), and "use a GitHub App installation access token or a personal access token instead" (**verified**, [GITHUB_TOKEN docs](https://docs.github.com/en/actions/concepts/security/github_token), fetched 2026-10-13). Our Mac-run publisher should push with an App installation token or PAT so S6 has checks to wait for. Copilot stops at *draft*; our S9 goes one step further (mark ready) — keep that as a deterministic node with its own guard.

## 6. Ranked shortlist — what to borrow or copy for our prototype

1. **S6 CI wait — copy Open SWE's check logic (MIT).** Port [`openswe/github/ci.py`](https://github.com/langchain-ai/open-swe/blob/0942b41561df7db968f3be7f1c5150819bdec6b8/openswe/github/ci.py) (`FAILING_CONCLUSIONS`, `CommitChecks`, `RequiredCheck.for_branch` incl. rulesets, `unreported_required_checks`) and `aggregate_check_state` + per-head-SHA retry counter + failure fingerprint from [`openswe/baby_sit.py`](https://github.com/langchain-ai/open-swe/blob/0942b41561df7db968f3be7f1c5150819bdec6b8/openswe/baby_sit.py) (L362-L410, L454-L535). Replace `RepoClient` with ~4 REST calls (`commits/{sha}/check-runs?filter=latest`, `commits/{sha}/status`, `branches/{b}`, `rules/branches/{b}`; see `openswe/github/http.py` L523-L556). On a dev Mac use polling (no public webhook URL). Unlike Open SWE, fetch the failed-job log **deterministically** (`actions/jobs/{id}/logs` or `gh run view --log-failed`), truncate it, wrap it as untrusted data (wording from `resources/prompts/runs/baby-sit-failure.md.jinja`) and route to S3; stop after N failures per head SHA. *Why:* production-hardened edge cases (no checks yet = pending; required-but-unreported = pending; cancelled/stale = blocked), zero LLM tokens while waiting.
2. **S5 publish — "agent returns a diff; trusted node publishes" (Codex two-job pattern ≈ OpenHands V0 resolver ≈ gh-aw safe-outputs).** Copy/adapt OpenHands [`send_pull_request.py`](https://github.com/OpenHands/OpenHands/blob/7bc3300981fa1cb4689d6e1b0c0bdd7fd77ac954/openhands/resolver/send_pull_request.py) (`apply_patch`, `make_commit`, `send_pull_request(pr_type="draft")`, `update_existing_pull_request`) (MIT); add gh-aw-style validation (protected paths e.g. `.github/workflows/**`, patch-size cap, branch/title conventions, one PR per task) and SWE-agent's [`OpenPRHook.should_open_pr`](https://github.com/SWE-agent/SWE-agent/blob/main/sweagent/run/hooks/open_pr.py) guards (issue still open, not locked, no other commits/PR already referencing it) (MIT). *Why:* the builder's worktree/sandbox never needs a GitHub token — our hard constraint — and every mature system converged on it (Codex docs, gh-aw, Copilot "cannot directly run git push").
3. **S7 reviewer — deterministic prep + read-only agent + schema-validated verdict.** Pattern from Open SWE's reviewer ([`openswe/reviewer.py`](https://github.com/langchain-ai/open-swe/blob/0942b41561df7db968f3be7f1c5150819bdec6b8/openswe/reviewer.py) `prepare_reviewer_run`; [`openswe/tools/add_finding.py`](https://github.com/langchain-ai/open-swe/blob/0942b41561df7db968f3be7f1c5150819bdec6b8/openswe/tools/add_finding.py); diff-line-set helpers in `openswe/review/diff.py`) + PR-Agent's schema fields (`merge_recommendation`, `ticket_compliance_check`, `key_issues_to_review`) from [`pr_reviewer_prompts.toml`](https://github.com/The-PR-Agent/pr-agent/blob/main/pr_agent/settings/pr_reviewer_prompts.toml) + Open SWE v1's forced two-tool verdict ([`final-review.ts`](https://github.com/langchain-ai/open-swe/blob/f1546093513aa49a5d88c8322a84a32452e537d3/apps/open-swe/src/graphs/reviewer/nodes/final-review.ts)). Verdict enum + findings anchored to diff lines + per-acceptance-criterion status, validated in code; reject out-of-diff findings. Route in code; bound rounds at 3 (v1 `maxReviewCount`).
4. **Graph shape — GitLab `fix_pipeline` / `issue_to_merge_request` as the design template (read, don't copy: EE licence).** Deterministic steps for every fetch/git action, agent components only for judgement, routers only over schema fields, per-node toolsets. Their `PRINCIPLES.md` lessons ("principles, not procedures"; fix failures in the layer that owns them; full, on-distribution checkouts) directly address our "prose state machine" problem.
5. **S3 builder runner — two viable options, both evidenced:** (a) `codex exec` subprocess in the task worktree (official ChatGPT login on a trusted machine; Seatbelt sandbox, network off by default; `--json` events; `--output-schema` for a structured "done" claim; `codex exec resume` to continue after an S4/S6/S8 bounce — pattern seen in IssueForge's `codex_executor.py`), or (b) an in-process `deepagents.create_deep_agent` loop with `LocalShellBackend`/Docker backend and `ModelCallLimitMiddleware`, using `langchain_openai`'s **private, experimental** `_ChatOpenAICodex` for ChatGPT OAuth (what Open SWE desktop and `dcode` do). (a) is lower-risk on auth/terms; (b) gives finer control and LangGraph-native streaming.
6. **S4 local gate — Aider's bounded reflection loop** (`--test-cmd`/`--lint-cmd`, failure output fed back, `max_reflections = 3`) as the policy, implemented as a deterministic node.
7. **X durability on a Mac — don't rely on `langgraph dev`.** Open SWE's [`local_checkpointer.py`](https://github.com/langchain-ai/open-swe/blob/0942b41561df7db968f3be7f1c5150819bdec6b8/openswe/local_checkpointer.py) documents that the dev server only pickles state every 10 s; run our graph as a plain Python process with `langgraph-checkpoint-sqlite` (or Postgres) and one `thread_id` per issue. (Durability details are another agent's area.)
8. **S1/S9/S10 safety checklist from Copilot cloud agent docs:** strip hidden characters/HTML comments from issue text before it reaches an LLM; only write-access users can trigger; single branch per task; draft first; never approve/merge; push with an App/PAT token (not `GITHUB_TOKEN`) so CI actually runs; post one sticky status comment (Claude Code Action pattern).

**Do not adopt:** Open SWE wholesale (agent-driven process, LangSmith-first sandbox/tracing, multi-tenant Postgres/Slack product, Agent Server licence for production standalone); GitLab code (EE licence); `deepagents` deploy examples (workflow lives in prose `AGENTS.md`); community LangGraph demos (≤10★, often auto-merge).
